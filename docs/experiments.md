# Experiment catalog: results, unfinished work and prior attempts

Updated September 19, 2026. This is the canonical status list for the ESP32-S3/TinyDraw browser, execution and hardware-timing investigations. Search here before starting another experiment. Each stable ID covers an idea family; aliases retain earlier branch, prototype and review names. Repeated runs and branch aliases stay with their existing idea family.

**Current position (September 19):** branch `night/combined-0919` (fork, not merged, no PR) runs the TinyDraw battery at **1.12× modeled real time** with bit-identical work and console output — 83.22→42.59 s over three alternating pairs against main d5446b4a — from virtual quanta (EX133/EX134), the dispatch diet (EX038, EX065, EX106), fewer special-register block boundaries (EX135) and much larger regions (EX136/EX137). pocket-tank, which keeps both cores busy, only reaches 0.44×. Branch `night/timed-0919` runs the approximate-timing model at about **1.0×** with measured control-flow, load-use, FP-readiness and fetch-alignment prices (EX138–EX142); its firmware timers are within about 4% of an erased-start board on the paced cold tests (compute median 0.964, wall 0.978), with document load (0.64) and ring-scalar staging (1.22) as the known misfits. Main itself is unchanged at about 0.55×. Sources: [EX133](#ex133), [EX137](#ex137), [EX141](#ex141), [Sep 19 log](evidence/overnight-2026-09-19/README.md).

**Beyond performance, the unfinished work is:** integrate and validate the separate prototypes that model when arithmetic results become usable; resolve the cache/bus, instruction-fetch and exception timing gaps; compare identical startup state; check the finished drawing against an independent expected image; verify that guest firmware reads every intended press/release; measure response time and device/interrupt deadlines. The full real-time, reset-to-display hardware-correlation goal is still unmet. Sources: [Scalar FP dependency readiness (EX057)](#ex057), [PIE Q-register dependency readiness (EX058)](#ex058), [CPU data-cache timing (EX051)](#ex051), [Matched ROM/IRAM call ladders (EX083)](#ex083), [Exception-rank follow-up (EX085)](#ex085), [Frozen full TinyDraw hardware reference (EX078)](#ex078), [Independent output and active-deadline correctness (EX123)](#ex123) and [Original full-product correlation and release goal (EX129)](#ex129).

The separate FP and Q scoreboards are outside that combined branch. **Reading the outcomes:** Worked means the stated bounded test succeeded; adoption is a separate column. Promising means favorable but insufficient confirmation. No gain means the stated test showed no useful improvement; that outcome applies to its workload and conditions. Invalid means the method cannot support its claim. Not tried, unbuilt and captured-but-unpriced are different states. “Not tried” means no completed result was found in the indexed sources. A plan's proposed priority expresses its recommended order of work; measured benefit comes from the experiment receipts.

FP means floating-point arithmetic. PIE is the ESP32-S3 vector instruction extension. A readiness scoreboard tracks when a prior instruction's result can be consumed. Host time is elapsed time on the computer; guest time is the emulator's modeled clock. A “price” is the cycle cost assigned to an operation. A differential test compares two execution implementations; matching them does not independently establish hardware truth. CUT is an early compiled-block exit/resume boundary.

## Keeping this list authoritative

Before proposing, implementing or benchmarking an idea, search the mechanism and aliases here. Cite the existing ID and state the material difference from prior attempts: changed mechanism, workload, correctness contract or stronger measurement. Record renamed branches as aliases of the existing idea. If an earlier patch exists, inspect it before rebuilding it.

Append a retry to the existing row, preserving the negative or inconclusive history. Record the runtime, baseline and candidate revisions, input state, exact work/output checks, measurement conditions, result, uncertainty and adoption status with a receipt. A correctness pass, favorable pilot, hardware capture and calibrated price are different claims. Report overlapping bundles as combined results. Compare throughput using equal work and matching timing models.

Use a new ID only for a materially different mechanism or validation question and link the related IDs. Keep IDs stable permanently. If new evidence contradicts an entry, update its outcome and preserve the superseded observation with its conditions. Link older plans here for current status. Experiment proposals remain proposals until explicitly selected for work.
